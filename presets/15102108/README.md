## 3. 짝 데이터셋과의 관계 (큐레이션 핵심)

두 관세 프리셋은 파라미터 이름도, 응답 항목 이름도 거의 같다. 자동생성 설명만으로는
LLM 이 "국가별"과 "총괄"을 고르지 못한다. 그래서 **양쪽 설명에 서로를 가리키는
문장을 넣었다.**

| | `15101612` 국가별 | `15102108` 총괄(이 번들) |
|---|---|---|
| 국가 코드 파라미터 | 있음(선택) | **없음** |
| 응답의 국가 코드·국가명 항목 | 있음 | **없음** |
| 골라야 할 때 | 특정 국가와의 실적, 국가별 순위·비교 | 국가 구분 없는 전체 총계, 월별 추이 |

## 4. 큐레이션이 바꾼 것 / 바꾸지 않은 것

**바꾼 것**

- 서비스 설명을 3문장으로 압축(원 `info.description` 은 무역통계 개론이다). 원문은
  `source.json` 의 `document.info.description` 에 그대로 있다.
- 오퍼레이션 요약·설명 + 짝 데이터셋 상호 참조 문장.
- 예시 프롬프트 2개, 파라미터 힌트 2종(시작·종료 연월).
- 응답 스키마를 **미확정으로 강등**(근거는 §5).

**바꾸지 않은 것**

- 파라미터의 타입·필수 여부, 경로, 메서드, base_url.
- 필수 파라미터의 예시값 — **어댑터가 채운다**(§6).

## 5. 응답 스키마를 미확정으로 강등한 이유

`15101612` 와 동일하다. 원 스펙의 200 응답 스키마는 (1) 실제 XML 보다 루트 래퍼가
한 겹 얕고, (2) 반복되는 항목 엘리먼트의 배열성을 표기하지 않았다. 틀린 스키마를
도구에 노출하느니 미확정으로 두고 추론에 맡긴다. 산출물의
`info.x-mcportal.schema_inference.unresolved` 가 `1` 로 나온다.

## 6. 실데이터의 지저분함(기록)

- `host` 에 경로가 들어 있고 `basePath` 가 빈 문자열이다(Swagger 2.0 위반). 포털
  관용 표기로 인정한다. 표준 검증기는 **산출 문서에만** 적용한다.
- **`definitions` 에 선행 공백이 붙은 오타 키(`' item'`)가 정상 키(`'item'`)와 함께
  존재한다.** `paths` 에서 참조되지 않아 무해하며, 실데이터가 얼마나 지저분한지를
  보여 주는 사례로 원문 그대로 보존한다. 두 정의는 내용도 미묘하게 다르다(오타 키
  쪽은 금액 항목 설명이 "수출미화금액"·"수입미화금액"이다).
- 표준 `parameters` 에 `example`·`default` 가 하나도 없고, 실제 예시값은 포털
  게이트웨이의 비표준 메타 블록에만 있다. 어댑터가 포털 공통 포맷으로 흡수해 빈
  `example` 만 채운다.
- 스칼라 리프마다 빈 `"properties": {}` 가 덧붙어 있다(정규화로 제거).
